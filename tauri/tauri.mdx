## Q1: Tauri 的历史？为什么要有它？

```text
┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  Electron    │ → │  Tauri 1.0   │ → │  Tauri 2.0   │ → │  Tauri 生态   │
│  内嵌浏览器   │   │  系统 WebView │   │  移动端支持   │   │  成熟发展     │
│  体积大       │   │  体积小       │   │  插件与权限   │   │  全平台覆盖   │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
```

<Steps>

  <Step title="早期: Tauri 项目启动">

    Tauri 由 Daniel Thompson-Yvetot 和 Lucas Nogueira 在 GitHub 上发起，核心动机是解决 Electron 的两大痛点：**包体积太大**（内嵌 Chromium 导致 150MB+）和**内存占用太高**（每个窗口 50-100MB）。Tauri 的核心创新是使用操作系统自带的 WebView（macOS 用 WKWebView，Windows 用 WebView2，Linux 用 WebKitGTK），后端用 Rust 实现，从根源上解决了 Electron 的资源浪费问题。

  </Step>
  <Step title="Tauri 1.0: 桌面端稳定版">

    经过几年的开发和社区打磨，Tauri 1.0 发布。1.0 版本支持 Windows、macOS、Linux 三大桌面平台，提供了窗口管理、文件系统访问、系统托盘、全局快捷键等核心能力。包体积通常在几 MB 到十几 MB（对比 Electron 的百 MB 级），内存占用也明显更低。

  </Step>
  <Step title="Tauri 2.0: 移动端支持">

    Tauri 2.0 是一个重大版本更新，核心新特性是**移动端支持**——同一套代码可以同时构建 iOS 和 Android 应用。此外还引入了插件系统 v2、IPC 性能优化、改进的安全模型等。Tauri 2.0 让开发者真正实现了"一份代码，桌面 + 移动端全覆盖"。

  </Step>
  <Step title="至今: 生态成熟与社区发展">

    Tauri 社区持续壮大，插件生态日益丰富。官方提供了 tauri-plugin-store（持久化存储）、tauri-plugin-sql（数据库）、tauri-plugin-notification（通知）等常用插件。社区也涌现了大量第三方插件和模板。Tauri 与 Next.js、SvelteKit、Vite 等前端框架的集成也越来越成熟。

  </Step>

</Steps>

**Tauri 解决的核心问题：**

```text
问题：Electron 的 Chromium 内嵌导致包体积大、内存占用高

Electron → 内嵌完整 Chromium → 包体积 150MB+ → 每个窗口 50-100MB 内存
→ 即使是简单的工具类应用，安装包也很大

解决：使用系统自带的 WebView + Rust 后端

Tauri → 系统 WebView（WKWebView/WebView2/WebKitGTK）→ 包体积几 MB 到十几 MB
→ 内存占用明显更低 → Rust 后端保证安全性和性能
```

<Note title="💡 一句话总结">

Tauri 使用操作系统自带的 WebView 替代 Electron 内嵌的 Chromium，后端用 Rust 实现，把桌面应用的安装包从百 MB 级压到几 MB 到十几 MB，内存占用也明显更低。

</Note>

<CardGroup cols={2}>

<Card title="🚫 没有 Tauri">

桌面应用开发只有 Electron 一条路——内嵌完整的 Chromium 浏览器，即使是一个简单的计算器应用，安装包也要上百 MB。就像你要运一个小包裹，却必须租一辆大卡车——能装，但浪费巨大。

</Card>
<Card title="✅ 引入 Tauri">

Tauri 使用系统自带的 WebView 渲染页面，就像用快递柜代替大卡车——包裹（Web 页面）通过系统已有的基础设施（WebView）送达，不需要额外搬运一整套浏览器。Rust 后端保证了安全性和性能，包体积只有几 MB。

</Card>

回答时先说"为什么"（Electron 包体积大、内存占用高），再说 Tauri 的核心思路（系统 WebView + Rust 后端），最后对比两者的包体积和内存数据。想听的是你对技术选型底层逻辑的理解，而不是背功能列表。

## Q2: Tauri 核心架构（Rust + WebView、前后端分离）

Tauri 的本质是**前后端分离架构**：前端用系统 WebView 渲染 Web 页面，后端用 Rust 实现应用逻辑和系统 API 调用，两者通过 IPC 通信。

│  │                                                       │  │

### Rust 后端

Rust 后端是 Tauri 的核心——它负责应用生命周期管理、窗口创建、系统 API 调用、IPC 消息处理。Rust 的编译期检查和零成本抽象，让 Tauri 在内存安全和执行性能上优于 Node.js。

```rust
// src-tauri/src/main.rs — Tauri 应用入口
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]

use tauri::Manager;

// Tauri 命令（Command）：前端可以通过 IPC 调用的 Rust 函数
#[tauri::command]
fn read_file(path: String) -> Result<String, String> {
    std::fs::read_to_string(&path).map_err(|e| e.to_string())
}

#[tauri::command]
fn get_system_info() -> SystemInfo {
    SystemInfo {
        os: std::env::consts::OS.to_string(),
        arch: std::env::consts::ARCH.to_string(),
        hostname: hostname::get().unwrap().to_string_lossy().to_string(),
    }
}

#[derive(serde::Serialize)]
struct SystemInfo {
    os: String,
    arch: String,
    hostname: String,
}

fn main() {
    tauri::Builder::default()
        .invoke_handler(tauri::generate_handler![
            read_file,
            get_system_info,
        ])
        .setup(|app| {
            // 应用启动时的初始化逻辑
            // v2 里窗口叫 WebviewWindow，通过 get_webview_window 获取
            let main_window = app.get_webview_window("main").unwrap();
            println!("应用已启动，主窗口: {:?}", main_window.title());
            Ok(())
        })
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

### 前端（WebView）

前端使用标准的 Web 技术（HTML/CSS/JS），可以搭配任意前端框架（React、Vue、Svelte 等）。通过 `@tauri-apps/api` 调用 Rust 后端的命令。

```javascript
// 前端代码 — 调用 Rust 后端
import { invoke } from "@tauri-apps/api/core";

// 调用 Rust 命令（双向 IPC 通信）
async function loadFile() {
  try {
    const content = await invoke("read_file", { path: "/path/to/file.txt" });
    document.getElementById("content").textContent = content;
  } catch (error) {
    console.error("读取文件失败:", error);
  }
}

// 获取系统信息
async function showSystemInfo() {
  const info = await invoke("get_system_info");
  console.log(`系统: ${info.os}, 架构: ${info.arch}, 主机名: ${info.hostname}`);
}
```

```javascript
// 前端代码 — 窗口管理
import { getCurrentWindow } from "@tauri-apps/api/window";

const appWindow = getCurrentWindow();

// 窗口操作
await appWindow.minimize();
await appWindow.maximize();
await appWindow.close();

// 监听窗口事件
await appWindow.onResized(({ payload: size }) => {
  console.log(`窗口大小: ${size.width}x${size.height}`);
});
```

```javascript
// 前端代码 — 事件系统
import { emit, listen } from "@tauri-apps/api/event";

// 前端发送事件给 Rust 后端
await emit("frontend-event", { message: "Hello from frontend!" });

// 监听 Rust 后端发来的事件
const unlisten = await listen("backend-event", (event) => {
  console.log("后端说:", event.payload);
});

// 组件卸载时取消监听
// unlisten();
```

### IPC 通信机制

Tauri 的 IPC 走 WebView 自带的消息通道：前端把命令名和参数序列化成 JSON 发给 Rust，Rust 处理完再把结果序列化回 WebView。常用两种模式：命令调用（invoke/command）和事件（emit/listen）。

| 通信模式           | 方向        | 前端 API              | Rust 端             | 特点              |
| ------------------ | ----------- | --------------------- | ------------------- | ----------------- |
| **invoke/command** | 前端 → Rust | `invoke('cmd', args)` | `#[tauri::command]` | 双向，返回 Result |
| **事件 event**     | Rust → 前端 | `listen('event', cb)` | `app.emit()`        | 单向推送          |
| **事件 event**     | 前端 → Rust | `emit('event', data)` | `app.listen()`      | 单向通知          |

注意：命令能否被调用由 capabilities 里的权限决定，未授权的前端调用会直接被拒绝。

### 系统 WebView 差异

Tauri 使用操作系统自带的 WebView，这意味着不同平台的 Web 引擎不同：

| 平台        | WebView   | 引擎            | 特点                                        |
| ----------- | --------- | --------------- | ------------------------------------------- |
| **macOS**   | WKWebView | WebKit (Safari) | 性能好，但某些 Web API 可能与 Chrome 有差异 |
| **Windows** | WebView2  | Chromium (Edge) | 与 Chrome 兼容性最好                        |
| **Linux**   | WebKitGTK | WebKit          | 功能最基础，某些 API 可能缺失               |

```text
注意：这意味着 Tauri 应用在不同平台上的 Web 渲染可能有细微差异

macOS (Safari 引擎)：
- CSS backdrop-filter 正常
- ES2022+ 特性支持较新
- 某些 Chrome 专有 API 不可用

Windows (Edge/Chromium 引擎)：
- 与 Chrome 兼容性最好
- 几乎所有 Web API 都可用

Linux (WebKitGTK 引擎)：
- 版本可能较旧（取决于系统）
- 某些新特性可能缺失
- 需要做更多的兼容性测试
```

<Note title="💡 一句话总结">

Tauri 的核心架构是前后端分离：前端用系统 WebView 渲染 Web 页面（任意框架），后端用 Rust 实现应用逻辑和系统 API，两者通过 IPC（invoke/command + emit/listen）通信。

</Note>

<Tip title="🎢 通俗比喻: 餐厅的前厅与后厨">

Tauri 应用就像一家餐厅。前端（WebView）是前厅——负责接待客人、展示菜单、上菜（渲染 UI），不同城市的分店（不同操作系统）用不同的装修风格（不同 WebView 引擎），但功能一样。后端（Rust）是后厨——负责采购食材（文件系统）、管理库存（系统 API）、处理订单（IPC 命令）。前厅和后厨通过对讲机（IPC）沟通——前厅把客人的需求传给后厨，后厨做好菜后通知前厅来取。

</Tip>

## Q3: Tauri vs Electron 对比（包体积、内存占用、安全性）

Tauri 和 Electron 的对比是面试中的经典问题——重点看你能否从多个维度做出有理有据的技术选型。

### 基础梳理

| 维度           | Electron                 | Tauri                      |
| -------------- | ------------------------ | -------------------------- |
| **渲染引擎**   | 内嵌 Chromium            | 系统 WebView               |
| **后端语言**   | Node.js                  | Rust                       |
| **包体积**     | 150-200MB                | 3-10MB                     |
| **内存占用**   | 150-400MB                | 30-100MB                   |
| **前端框架**   | 任意 Web 框架            | 任意 Web 框架              |
| **移动端支持** | 不支持                   | Tauri 2.0 支持 iOS/Android |
| **Web 兼容性** | 最好（就是 Chrome）      | 取决于系统 WebView 版本    |
| **原生模块**   | npm 生态（Node.js）      | Rust crate 生态            |
| **学习曲线**   | 低（只需 Web + Node.js） | 中等（需要学习 Rust 基础） |
| **生态成熟度** | 非常成熟（十余年积累）   | 快速成长中                 |

### 专家视角深度剖析

很多人只能背诵上面的表格，但实际更在意的是：**在什么场景下选 Tauri，什么场景下选 Electron？**

选型的核心不是"哪个更好"，而是"哪个更适合你的项目"：

**选 Electron 的场景：**

- 团队只有前端技术栈（HTML/CSS/JS + Node.js），没有 Rust 经验
- 应用需要复杂的系统集成（深度调用操作系统 API）
- 需要最好的 Web 兼容性（应用内嵌复杂 Web 内容）
- 已有成熟的 Electron 应用，迁移成本大于收益
- 社区生态和插件支持是关键需求

**选 Tauri 的场景：**

- 对包体积和内存占用有严格要求（如工具类应用、嵌入式设备）
- 团队有 Rust 经验或愿意学习 Rust
- 需要同时覆盖桌面和移动端（Tauri 2.0）
- 安全性要求极高（Rust 的内存安全保证）
- 应用功能相对简单（不需要复杂的 Web 渲染）

```text
选型决策树：

需要同时覆盖桌面 + 移动端？
  └─ 是 → Tauri 2.0
  └─ 否 → 继续判断

团队有 Rust 经验？
  └─ 是 → 对包体积/内存有要求？
  │       └─ 是 → Tauri
  │       └─ 否 → 都可以，看生态需求
  └─ 否 → 需要最好的 Web 兼容性？
          └─ 是 → Electron
          └─ 否 → 考虑学习 Rust，选 Tauri
```

```text
量级对比（不是基准测试，具体数字随应用和平台差异很大）：

Electron
- 安装包：百 MB 级（内嵌完整 Chromium 与 Node.js）
- 内存：每个窗口一个渲染进程，窗口越多占用越高
- 冷启动：需要初始化 Chromium，通常更慢

Tauri
- 安装包：几 MB 到十几 MB（复用系统 WebView，不含浏览器内核）
- 内存：复用系统 WebView，通常明显更低
- 冷启动：省掉浏览器内核初始化

差距原因：
Electron 内嵌了完整的 Chromium，每个窗口是独立渲染进程
Tauri 使用系统已有的 WebView，Rust 后端更轻量
```

### Tauri 2.0 新特性（移动端支持）

Tauri 2.0 的核心新特性是移动端支持——同一套前端代码可以同时构建 iOS 和 Android 应用。

```text
Tauri 2.0 平台覆盖：

┌─────────────────────────────────────────────────┐
│                 前端代码（Web 页面）               │
│           React / Vue / Svelte / 任意框架         │
└───────────┬─────────┬─────────┬─────────┬───────┘
            │         │         │         │
   ┌────────▼──┐ ┌────▼────┐ ┌─▼──┐ ┌───▼──┐
   │  macOS    │ │ Windows │ │iOS │ │Android│
   │  WKWebView│ │WebView2 │ │ WK │ │ Web  │
   │  Rust     │ │  Rust   │ │Rust│ │ Rust │
   └───────────┘ └─────────┘ └────┘ └──────┘
```

```rust
// Tauri 2.0 移动端 — Rust 代码与桌面端共享
// src-tauri/src/lib.rs

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .plugin(tauri_plugin_shell::init())
        .plugin(tauri_plugin_notification::init())
        .invoke_handler(tauri::generate_handler![
            read_file,
            get_system_info,
        ])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

```javascript
// 前端代码 — 平台自适应
import { platform } from "@tauri-apps/plugin-os";

async function loadFile() {
  const os = platform();

  // 不同平台的文件路径可能不同
  const path =
    os === "ios"
      ? "/var/mobile/Containers/Data/Application/.../file.txt"
      : "/Users/.../file.txt";

  const content = await invoke("read_file", { path });
}
```

<Note title="💡 一句话总结">

Tauri vs Electron 的核心差异：Tauri 用系统 WebView + Rust（包体积 3-10MB，内存 30-100MB），Electron 用 Chromium + Node.js（包体积 150MB+，内存 150-400MB）。选型取决于团队技术栈、Web 兼容性需求和包体积要求。Tauri 2.0 支持移动端。

</Note>

## Q4: Tauri 插件系统

Tauri 的插件系统是扩展应用能力的核心机制——它允许开发者用 Rust 编写插件，为前端提供新的命令和 API。

use tauri::{
    plugin::{Builder, TauriPlugin},
    Runtime,
};

#[derive(serde::Serialize)]
struct SystemMetrics {
    cpu_usage: f32,
    memory_used: u64,
    memory_total: u64,

#[tauri::command]
fn get_system_metrics() -> SystemMetrics {
    // 使用 sysinfo crate 获取系统指标
    let mut sys = sysinfo::System::new_all();

        memory_used: sys.used_memory(),
        memory_total: sys.total_memory(),
    }
}

/// 初始化插件
pub fn init<R: Runtime>() -> TauriPlugin<R> {
    Builder::new("system-monitor")
        .invoke_handler(tauri::generate_handler![get_system_metrics])
        .build()
}

### 权限配置

Tauri 2.0 引入了基于权限的安全模型——插件的每个能力都需要在配置文件中显式声明。

```jsonc
// src-tauri/capabilities/default.json
{
  "identifier": "default",
  "windows": ["main"],
  "permissions": [
    "core:default",
    "shell:allow-open",
    "fs:allow-read-text-file",
    "fs:allow-write-text-file",
    "store:default",
    "notification:default",
    "system-monitor:allow-get-system-metrics",
  ],
}
```

读文件除了 `allow` 权限，通常还要配 `fs:scope` 之类的 scope 才能限定可访问的目录；自定义插件的权限名是 `插件名:allow-命令名`（命令名转 kebab-case）。

Tauri 的插件系统用 Rust 编写，通过 `tauri::plugin::Builder` 注册，前端通过 `invoke('plugin:name|command')` 调用。官方提供了 store、sql、notification 等常用插件，自定义插件只需实现 `#[tauri::command]` 函数并注册。

## 🔍 底层源码：Tauri 是如何实现的？

<div class="follow-up">Tauri 的 IPC 消息是如何在前端和 Rust 之间传递的？</div>

Tauri 的 IPC 底层依赖 WebView 提供的消息通道（[tauri-core/src/ipc](https://github.com/tauri-apps/tauri/tree/dev/core/tauri/src/ipc)）。前端调用 `invoke()` 后，命令名和参数被序列化成 JSON，通过 WebView 的消息通道或自定义协议传给 Rust 后端：

```text
伪代码：Rust 端处理一次 IPC 调用

1. 从 WebView 收到一条 IPC 消息（命令名、参数、调用 id）
2. 按命令名在 invoke_handler 的注册表里查找处理函数
3. 把 JSON 参数反序列化成该函数声明的参数类型
4. 执行命令，把返回值序列化为 JSON
5. 通过消息通道把结果和调用 id 回传，前端 resolve 对应的 Promise

命令未注册 → 回传错误信息，前端 reject
```

前端的 `@tauri-apps/api` 包内部把 `invoke()` 转成 IPC 调用；具体的传输方式由 WebView 提供（自定义协议或 message handler，各平台实现不同），Rust 端收到后按命令名分发。

<div class="follow-up">Tauri 的权限系统是怎么实现的？</div>

Tauri 2.0 的权限系统实现在 `tauri-utils/src/capability`（[源码](https://github.com/tauri-apps/tauri/tree/dev/core/tauri-utils/src/capability)）。每个命令在执行前都会经过权限检查：

```text
伪代码：一次命令调用的权限检查

1. 取出当前窗口对应 capability 里声明的权限列表
2. 拼出这次调用需要的权限标识（如 fs:allow-read-text-file）
3. 列表里命中该标识 → 放行
4. 命中该插件的通配或 scope 权限 → 放行
5. 都没有命中 → 拒绝，返回 permission denied
```

权限声明存储在 `capabilities/*.json` 文件中，应用启动时加载并缓存。每个窗口可以有不同的权限集——这实现了**最小权限原则**：每个窗口只能访问它需要的能力。

## 及格回答 vs 满分回答

### 问题："说说 Tauri 和 Electron 的区别，你会怎么选？"

**及格回答（60-70分）：**

> "Tauri 用系统 WebView，Electron 用 Chromium，所以 Tauri 包体积更小、内存占用更低。Tauri 后端用 Rust，Electron 用 Node.js。"

问题出在：**知道基本差异但不理解选型逻辑**。

**满分回答（90-100分）：**

> Tauri 和 Electron 的核心区别在于**渲染引擎和后端语言**。Electron 内嵌完整的 Chromium 浏览器，Tauri 使用操作系统自带的 WebView（macOS 用 WKWebView，Windows 用 WebView2，Linux 用 WebKitGTK），系统 WebView 已经存在于用户的操作系统中，不需要额外打包。量级上，Electron 的安装包在百 MB 级，Tauri 通常在几 MB 到十几 MB；内存方面，Electron 每个窗口是独立的 Chromium 渲染进程，Tauri 复用系统 WebView，整体更轻。<sup>[1]</sup>

> 后端语言的选择影响了安全性和性能。Rust 在编译期消除数据竞争、悬垂指针这类错误，而 Node.js 主要靠运行时检查。对于长期运行的桌面应用，少一类内存错误就少一类线上崩溃；但内存泄漏在 Rust 里并未被完全禁止，仍要靠设计规避。代价是学习曲线——团队需要学习 Rust 的所有权和生命周期概念，这对纯前端团队是一个不小的挑战。<sup>[2]</sup>

> 选型建议：如果团队只有前端技术栈、应用需要复杂的 Web 渲染（如内嵌 iframe 加载第三方内容），选 Electron——它的 Web 兼容性最好（就是 Chrome），生态最成熟。如果对包体积有严格要求（如工具类应用需要小安装包）、团队愿意学习 Rust，选 Tauri。如果需要同时覆盖桌面和移动端，Tauri 2.0 是唯一的选择——Electron 不支持移动端。

> 社区里也有团队分享过类似的迁移：安装包从百 MB 级降到个位数 MB，内存占用明显下降。迁移的主要成本不在前端，而是把 Node.js 的文件系统、数据库和系统集成逻辑重写成 Rust，前端代码通常只需要替换 IPC 调用。
